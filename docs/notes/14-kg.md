# Legal KG (rule-built, updatable) — 2026-11-19

Build: `python -m cli kg-build` → `data/kg/kg.sqlite` (SQLite, `src/kg/store.py`, 6 unit tests). No framework and no LLM: vbpl.vn metadata
(`data/raw/vbpl/metadata.parquet`: validity status + effective dates) and `relationships.parquet` (1.03 M rows, 31 relation names) are already
structured. 171,556 documents, 989,692 undirected edges; relation names grouped into families amends / replaces / repeals / expires / guides /
bases_on / cites / other (`FAMILY`).

Facts that shaped the design
- Law numbers are NOT unique: 171k documents share 70k keys (84 provincial "01/2024/QĐ-UBND", 458 "Không số") → nodes keyed by vbpl `id`, queries by
  law key return every document with that key.
- vbpl lists each relation on both documents under an active and a passive name; the direction of each raw name is not verified → edges are stored
  undirected per (family, raw name). Direction (who amends whom) needs checking against document dates before a tool states it.
- Update operations (idempotent): `upsert_doc`, `add_edge`, `remove_doc`; `valid_on` / `neighbors(as_of=...)` filter by effective dates (temporal queries).
  The vbpl snapshot is static: fresh documents need a new crawl; the vector index has no incremental path yet (FAISS flat supports add / remove).
- Tool candidates: `amendments(key)`, `get_cited(key)` (Điều-level cites still need a regex pass over article text), `neighbors(key, families, as_of)`.

Evidence for value (dev / test, A2e retrieval)
- Gold Điều is in top-5 for 90 % of questions; of the 25 dev / 18 test misses 16 / 11 do not retrieve the gold law at all, and the gold law is one hop
  from a retrieved law in 11 / 7 of them — but "Căn cứ" edges are dense, so chance overlap is not excluded (control not yet run).
- 62 / 281 dev gold laws are "Hết hiệu lực toàn bộ" (151 "một phần"): reference answers seem to use old text → a validity tool defaulting to "today" could
  hurt; keep `as_of` = the reference's date.
- Upper bound of gain through retrieval misses ≈ +.015 rougeL (11 questions × (.70 − .295) / 300); wrong-Điều selection among top-5 matters more.
Next: chance control for the one-hop statistic; static neighbour-document expansion vs a k=10 control; direction check; ReAct tool wrapper after the baseline.

## Tool `kg_related(law, hops)` (built test-first, 2026-11-19)
- The model chooses `hops`; it is ADVISED (tool description + system prompt) to use 1–2. datamate found notes inside tool output are followed in 0–2 % of
  cases, so the size limit does not depend on advice: per hop ≤ 5 documents, ≤ 12 overall (`KG.related(per_hop, max_total)`), `MAX_HOPS = 4` clamp, and the
  result always states the TRUE count per hop ("hop 3: 378 văn bản, hiện 5") so a large hop is visible.
- Hop growth (172 dev gold laws, amends/replaces/repeals/expires): new documents median/p90 = 3/8 (hop 1), 4/25 (hop 2), 6/81 (hop 3); with "guides" added hop 3 reaches
  median 378 — hence guides and bases_on are not in the default families ("Căn cứ": a law can be the basis of 8,672 documents).
- Unknown law → `None` ("Không tìm thấy"), known law with no relation → `[]` ("Không có ..."), so the model can tell the two apart.
- Which questions could profit (v0 dev, 281 questions with a gold law): multi-law questions 60 (21 %, rougeL .480 vs .650; gold laws linked in the KG for 46, via
  amend/replace/repeal/expire/guide for 34); gold law missed but one hop from a retrieved law 10 (.263). Ceiling ≈ +.01–.03 rougeL; comparison is correlational.
- Arms (config `generate.agent_tools`): [search_law, get_article] · [get_article, kg_related] · all three; each against a non-agent control with the same extra passages.
